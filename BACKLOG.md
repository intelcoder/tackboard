# Backlog

Things that were found, decided against for now, or left open when v1 was wrapped up. Nothing here blocks using the tool. Each item says where to look and, where it matters, how it was found. Pick one, check it is still true, and delete it from this file when it is done.

Priority: **P1** can lose or confuse a user's data or work. **P2** is a visible rough edge. **P3** is cosmetic or an idea.

## Daemon and API

- **P2: no limit on `url`, `element.tag` and `element.component`** in a posted comment (only `html`, `selector` and `text` are capped). Anyone with the token can make the agent's output large. `packages/daemon/src/interface/http.ts`, `packages/shared/src/api.ts`.
- **P2: the thread list is heavy at large sizes.** Each poll runs three `git` child processes (about 37 ms with no threads) and sends every thread with its `html` (22 MB per poll at 5 000 threads, about 0.5 s of daemon stall). Ideas: cache the branch, leave `html` out of list rows, `ETag` or a `since` parameter. `packages/daemon/src/application/queries/list_threads.ts`, `infrastructure/git_info.ts`.
- **P3: no poll backoff** when the daemon is down, and no pause for a hidden tab (the overlay polls every 1.5 s while any mode other than hidden is on).
- **P3: `HEAD` on the token-free paths returns 401**, where `GET` is the only open method. Harmless, and not covered by a test.
- **P3: a refused agent resolve and an already-resolved thread** now answer 409 `waiting_on_user`, not 400. The code name no longer describes the reason; the message does.
- **P3: agent-started comments** (`tackboard comment`) are stored with an empty page address and an empty tag. The overlay treats an empty address as "any page" and an empty tag as "any element". Recording the real page would be cleaner.

## Overlay

- **P2: a retried send can be stored twice.** After "The daemon did not answer" the message may already have arrived, and Retry then posts it again. The README says so. A fix needs an id the daemon can recognise (an idempotency key); it was left out to keep the change small.
- **P2: the send queue and the drafts live in the page.** Both are lost on reload. No persistence by design; drafts kept in the daemon would survive a reload but add a draft state to threads, the API and the CLI.
- **P3: drafts are minimal.** They show only in the panel (no pins on the page), cannot be edited (remove and add again), and Send all creates one ordinary thread per draft. Drafts sent together are taken together by `next` and `wait` unless the agent asks between two sends; a batch id on the threads and a short wait before the claim were left out on purpose (the id would change the frozen thread type, the database, the API and the overlay, and still would not stop an agent that asks between two sends; the wait delays every single comment). After Send all the panel switches to View mode and opens the last thread, which interrupts a batch flow.
- **P2: Resolve (and the reply box) can need a scroll in the short panel**, for example with the notification banner showing and a long thread. A sticky action row would fix it.
- **P3: the margin, padding and gap strips** are drawn outside a scroll container for an element partly scrolled out of it, are wrong for `transform: scale()` (they use CSS pixels around the scaled box), and show vertical margins on inline elements. On macOS holding Control then clicking opens the browser's context menu, so release Control before picking. `packages/overlay/src/spacing.ts`.
- **P3: two comments on the same element** put their pins at the same spot; one covers the other. Both are reachable from the panel.
- **P3: a pin can linger for up to one poll (1.5 s)** after its element leaves the page, and a text-matched element keeps its pin if its text changes in place.
- **P3: threads from other pages** are listed under "Element missing" in the panel.
- **P3: queue details:** a queued reply is hidden when another thread becomes the active one; Retry and Remove sit partly clipped at the bottom of the list until you scroll; two stacked "Cannot reach the daemon" banners can appear.
- **P3: dark-mode contrast:** white text on the amber and green fills measures about 1.9:1.
- **P3: restore marker and banner:** the restore marker reads "after message 1·" (the space collapses and the hash is cut), and the blocked-notification banner's Dismiss button wraps onto its own line at 320 and 390 px.
- **P3: `destroy()` aborting an in-flight send** and clearing a held Control key have no tests.

## CLI and docs

- **P3: claims of a batch go stale together.** `next` and `wait` claim every pending thread in a row, so all of them are claimed at about the same time and can all be claimed again after 30 minutes (`claim_all_pending` in `packages/cli/src/commands.ts`). The README says so.
- **P3: two agents asking at the same instant can split a batch.** Each claim is atomic, so every thread still goes to exactly one agent, but the agents may each get some. The claims are one call each, not one step (`packages/daemon/src/application/commands/claim_next_thread.ts`).
- **P3: every claim and every reply that changed files takes one git snapshot** (`claim_next_thread.ts`, `reply_to_thread.ts`, `checkpoints.snapshot`). About 0.1 to 0.2 s each on a 450-file repository, measured by the planner on a local clone; larger repositories take longer. The claim snapshots of one batch are the same state, but each still costs a git call.
- **P3: `tackboard next` cannot take just one thread**, and there is no flag for it. No test or user flow needs one. Its requests to the daemon have no timeout (`packages/cli/src/client.ts`, as before).
- **P3: two test gaps for `next`.** No test pairs a restore notice with two or more threads in one `next` (checked by hand once: the notice printed once, first). The last assertion of `e2e/tests/claim_race.spec.ts`, `got + none === 10`, is weak alone; the assertions before it (each posted id printed once) carry the promise.
- **P3: restore after a batch is written in the README as what the code does, and no test pins it** (the user chose to skip those tests). Restoring to a reply returns to just after that reply; restoring to a batch thread's own comment returns to the state when the batch was claimed (`reply_to_thread.ts`, `restore_to_message.ts`). The planner checked it once, and T55 ran it again in a throwaway project with a real daemon and Playwright's Chromium (restore to the reply of the first thread, and to the first comment of a batch). Not run: restore to the last comment of a batch.
- **P3: a restore does not change the status of the threads that stay.** A thread whose reply was discarded still reads `waiting on you` (`Thread.discardAfterSeq`, `restore_to_message.ts`). Also seen in T55's run: restoring to the first comment of a batch discards every later comment, so the other threads of the batch are discarded too (the notice names them), because "later" counts across the whole branch.
- **P3: two lines of the batch instruction block are pinned by no test:** the `Hint` line and `Only change what each comment asks` (`formatThreads` in `packages/cli/src/format.ts`). The tests pin the count line, the first heading, the reply and question lines and `Only the user closes a thread.`
- **P3: naming note:** the function that prints one thread's instruction block is `threadInstructions` (`packages/cli/src/format.ts`), written camelCase like `formatThread` next to it, while newer CLI code uses snake_case (`claim_all_pending`, `usage_commands`). The plan called it `thread_instructions`. Rename them together if the file is ever tidied.
- **P3: the batch is claimed together, in the agent's CLI, not in the daemon.** Left out on purpose: an atomic "claim all" endpoint in the daemon (decided against in T50; the cost is the per-claim line above), and making the claims of a crashed agent's batch claimable before the 30 minutes are over (`claim_all_pending` in `packages/cli/src/commands.ts`).
- **P3: small CLI rough edges:** `wait --timeout -1` prints a raw argument error; `--mention you` is silently ignored; `--port 1e3` and `0x10` are accepted as ports; a corrupt `.tackboard/config.json` gives a raw parse error; the restore notice shows raw ids ("message t3/m1") where the panel says "message 1"; when `SKILL.md` is a directory, `init` says "left as is"; the usage line for `channel` is not pinned by any test.
- **P3: the skill and the README repeat the loop, the "only the user closes a thread" rule and the worktree explanation.** A test checks the command names only, so the copies can drift apart.
- **P3: `tackboard` is not on your PATH** until you run `npm link -w packages/cli`; the package is private and not published. Publishing (a built CLI, a versioned overlay file) is not done.

## Claude Code channel

- **P2: channels are a research preview.** The start flag (`--dangerously-load-development-channels`) and the dialogs may change, and they need claude.ai or Console login (not Bedrock, Vertex or Foundry) and, on Team and Enterprise, an owner switch. Re-check https://code.claude.com/docs/en/channels.md when upgrading Claude Code. The server answers protocol versions up to 2025-11-25; the docs describe `MCP_PROTOCOL_NEGOTIATION=legacy` for the newer revision.
- **P3: the channel only works in an interactive session** (the docs say the flag is ignored with `-p`).
- **P3: a comment is delivered once** only until its claim goes stale (30 minutes); then it can be claimed and sent again.
- **P3: idea, tools for the agent.** A channel with tools (reply, comment) instead of shell commands. Not needed: the CLI works with every agent.
- **P3: idea, WebSocket or Server-Sent Events** between the daemon and the page instead of polling. Browsers cannot set a header on either, so the token would have to move into the URL or a first message. Left out because the page cost was the real problem, and that is fixed.

## Playground

- **P3: a hard link to an outside file is served.** The playground server serves only `<copy>/site/` and checks the real path of every file, which closes every symlink case, but a hard link (`ln`, not `ln -s`) made inside `site/` to a file elsewhere on the same disk (for example the daemon's token file) looks like an ordinary file and is served. Only an agent working in the throwaway copy can make one. The daemon also gives the token to any allowed page in its own bundle, by design.

- **P3: an interrupted e2e run can leave daemons behind.** `startStack` in `e2e/tests/extension.spec.ts` starts the daemon through the CLI (`node cli start`) and stops it only in `stop()`, so Ctrl+C on a test run can leave `tb-ext-*` daemons running. Reported by a reviewer, not reproduced. The other specs start theirs the same way (`startHarness` in `e2e/fixtures/harness.ts`); check them too.
- **P3: playground tests leave the daemon behind when they fail.** The `finally` blocks of most tests in `e2e/tests/playground.spec.ts` stop only the playground, and the daemon runs in its own process group, so a failing test leaves a daemon running (passing runs are clean). The SIGHUP test already records and kills its own pids; the others could do the same.
- **P3: `SIGKILL` of the playground** leaves its daemon running (no program can handle it). Stop it with Ctrl+C, SIGTERM or SIGHUP.
- **P3: SIGTERM during a reset** can still print the done line although the daemon is deliberately not restarted while leaving.

## Chrome extension

- **P2: screenshots were not run in real Chrome.** The Playwright test proves the crop, the size and that the overlay is not in the picture, with `<all_urls>` built into the test extension. Not seen in real Chrome: the approval box for **Allow screenshots** (and the warning text it shows), `captureVisibleTab` on a page the user added, a zoomed page, a retina screen, and an element inside a scrolled container. The crop uses the picture width over `innerWidth`, which should cover zoom and retina but is not measured. `packages/overlay/src/screenshot.ts`, `packages/extension/src/options.ts`.
- **P3: screenshots have no thumbnail on the thread, no edit, and only the first comment of a thread can carry one.** The panel cannot show the file because the daemon's answers pass through the extension as text. Replies take no screenshot. Not on the script tag route (no way to capture a tab) and not inside frames.
- **P3: a failed screenshot keeps the comment box open** and shows a toast; the comment is not sent. Chosen over sending without the picture, so the agent never gets less than the user asked for.
- **P3: the screenshot files are never deleted** (not on resolve, not on restore). They are in `.tackboard/`, which is outside git.

- **P2: not run by hand in real Chrome.** The agent could only drive Playwright's Chromium. Never seen in real Chrome: the approval box from `permissions.request`; a real `permissions.remove` after Remove; dark mode of the options page; the options page error lines; the Chrome screens the README names (`chrome://extensions`, Load unpacked, Details, Extension options, the reload arrow), which are written from Chrome's documented behaviour. The e2e builds the extension with the test sites already approved (`extraHostPermissions` in `packages/extension/build.ts`). With the plain build (`packages/extension/dist/`) in Playwright's Chromium, `Add a site` saved nothing and showed no line for 6 seconds, because nobody could answer the box. Before a release, add a site by hand in Chrome, then Remove it, and look at `chrome://extensions` for the site access.
- **P2: the click's user gesture may not survive the `await permissions.contains`** that runs before `permissions.request` (`packages/extension/src/options.ts`, the submit handler). If Chrome then refuses the request for lack of a gesture, every add shows `Chrome did not allow that site`. Not seen in real Chrome.
- **P3: the undo branch is not tested.** `if (!hadIt) ...permissions.remove` after a failed registration (`options.ts`) cannot be reached by a test under the pre-approved build. The e2e proves the failure itself with a stub of `registerContentScripts` (`e2e/tests/extension.spec.ts`, last test).
- **P3: a `null` entry in the saved sites crashes the options page** (`showSites` in `options.ts` reads `sites[origin]!.on`). Only this extension writes that key, so it needs a bug or a hand edit to happen.
- **P3: an unknown or malformed message from the content-script side gets no reply** (`packages/extension/src/proxy.ts`, `background.ts`). A web page cannot send one, because pages have no way to message the extension; the cost is a call that waits.
- **P3: a failed re-add can leave a saved site with no script and no message.** `options.ts` unregisters the old script before it registers the new one, so if Chrome rejects the register step for a site that was already added, the old script is gone while the site stays saved and listed as `On`: no bar, no hint. Adding the site again fixes it. When two added sites share a host pattern (`http://localhost/*` for any port), they share one script id, so both lose it. A cheap fix: for an existing id call `chrome.scripting.updateContentScripts` instead of unregister then register, or register the old script again in the `catch` (`options.ts`, the submit handler).
- **P3: a frame is answered with the settings of the TAB's page, not its own.** The background reads `sender.tab.url`, so a frame of another added host, or of another port of the same host (a permission pattern ignores ports), inside an added page talks to the page's daemon with the page's token; a frame of an added host inside a page that was not added gets nothing (`packages/extension/src/background.ts`, `proxy.ts`). A possible tightening: compare the frame's own origin with the tab's before answering true. Shown by the T54 tests and by a run in T55 (a frame on another port of `localhost` got the bar). Not tried: `sender.tab.url` for very deep or extension-owned frames.
- **P2: `clipboardRead` adds an install-time warning** (Chrome words it as "Read data you copy and paste"; that is Chrome's documented text, not seen here). The options page reads the clipboard once when it opens with `?site=`, and only fills an empty Config box with text that reads as a config (`options.ts`). Decide before a release whether the warning is worth it; the cost of dropping it is that the user pastes the config by hand.
- **P2: real Chrome items not tried in the frames, clipboard and toolbar work:** the `clipboardRead` install or update warning; the real approval box; a real `permissions.remove` on Remove; the real toolbar click; `activeTab` giving the address of a page that was not added; how the badge looks; pinning the button; which update events real Chrome sends in every navigation case (the badge refresh relies on `status` and `url`, `badgeNeedsUpdate` in `toolbar.ts`); `sender.tab.url` for very deep or extension-owned frames. The clipboard fill and the frames were run only in Playwright's Chromium.
- **P3: the badge title for a web page that was not added is rarely visible.** Chrome hides the address of a tab the extension has no access to, so `badgeFor` (`packages/extension/src/toolbar.ts`) usually gets no address and gives `click to open the site list.`; `this site is not added. Click to add this site.` shows only where the address is readable (a granted host that is not saved, as in the e2e).
- **P3: the e2e rule the user set:** an e2e test is only for what unit and integration tests cannot prove (a real browser, real Chrome APIs, real DOM or performance, several processes together, cross-origin security). Exact wording is not pinned in e2e when a unit test pins it. A planned audit of the e2e tests (175 runs when this was written; some tests run several times) will sort them into: keep, cut the duplicated assertion, and move down to a unit test.
- **P3: waiting for the user's own Chrome check** of the missing bar on a test site: whether it was caused by the extension's site scripts not being registered again when the extension starts. Not touched. If it is, register them on start (`packages/extension/src/background.ts`).
- **P3: Chrome Web Store publishing is not done.** A store build gets its own id, so `brand.extensionOrigin` (`packages/shared/src/brand.ts`) would have to list two origins, and `packages/daemon/src/interface/http.ts` allows only one.
- **P3: Firefox and Safari are not supported** (the manifest and `chrome.*` calls are Chrome's).
- **P3: no settings sync, import or export** of the site list; the sites and the token live in `chrome.storage.local` of one profile (`packages/extension/src/chrome_calls.ts`).
- **P3: no per-page rules.** The choice is per site address, so one page of a site cannot be left out.
- **P3: React component names are lost in the extension.** A content script's separate JavaScript world cannot see React's data on elements (`packages/overlay/src/source_map.ts` line 19, `Object.keys(el)`). From Chrome's documented rule; not measured in a real page. The `data-tb-src` attribute route is read with `getAttribute`.
- **P3: Chrome's approval is per host name and ignores the port.** `permissions.request` patterns have no port (`siteFrom` in `packages/extension/src/sites.ts`), so one approval covers every port of that host. The bar still shows only on the saved address.
- **P3: the toolbar button has no popup and no icon image** (`action` in `packages/extension/build.ts` has only a title; Chrome draws the first letter of the name). A click does the one useful thing (`packages/extension/src/toolbar.ts`, `background.ts`). A click does not reload the tab on purpose: the open tab follows through the `changed` message, and a reload would throw away the page's unsent drafts and send queue.
- **P2: a real toolbar click and `activeTab` were not run in real Chrome.** `e2e/tests/extension.spec.ts` (the toolbar tests) raises the same `chrome.action.onClicked` event with `dispatch`, so it proves the handler, the saved flip, the badge and the options page, not that Chrome delivers a real click to the listener, nor that `activeTab` gives the address of a page that was not added (the e2e build has the test sites pre-approved, so their addresses are visible anyway). Before a release: click the button on an added site, on a site that was not added and on `chrome://extensions` in real Chrome.
- **P3: the toolbar badge and the pin were not looked at in real Chrome.** The tests read the badge text, its text colour and the title back from the extension, not what Chrome draws (`badgeFor` in `packages/extension/src/toolbar.ts`). Pinning the button from the puzzle-piece menu is written in the README from Chrome's documented behaviour and was not tried.
- **P3: the `chrome.tabs.onActivated` listener in `packages/extension/src/background.ts` has a unit test only for a tab that closed before it ran** (`packages/extension/test/background.test.ts`). No test checks the badge it sets for a tab that was open before the extension loaded.
- **P3: a fast burst of toolbar clicks loses updates.** Each click loads the saved sites, flips one and saves them (`chrome.action.onClicked` in `background.ts`), so 20 clicks in the same tick overlap and some flips are lost (shown by the T49 verifier with 20 `dispatch` calls in one tick, 6 runs of 6). A person cannot click that fast.
- **P3: the content script is loaded in every frame of every page of an added host** (`allFrames` in `packages/extension/src/options.ts`) and asks the background once whether the site is on (`packages/extension/src/content.ts`, `background.ts`), including other ports of the same host.
- **P3: the local-network prompt is untested.** The README says Chrome's newer local-network permission prompt may block the script tag route on a public `https` domain; the extension route was the only one tried.

## Names (the rule: easy everyday words, no jargon)

- **P3: names left after the plain-names pass.** Kept on purpose: `h`, `H` and `createH` (`h` is also a height in many places, so a blind rename is unsafe), the CSS classes `tb-crumbs` and `tb-convo` (browser tests select them), the `job` field on queue items. Cryptic names a reviewer still found, with a plainer one: `crumbs2` and `chain` (hover.ts) -> `parents`, `kept` and `finder` (element_ref.ts) -> `foundElements`, `snap`, `lit`, `lastLook`, `settle`, `poller` in tests and helpers -> `savedState`, `highlighted`, `lastSeen`, `waitUntilStill`, `pollTimer`, `evil` and `fakeSend` and `withStub` in tests -> `badInput`, `pretendSend`, `withFakeDaemon`, `px` -> `pixels`, and the `box` variable in `thread_view.test.ts` -> `replyBox`. The `fiber` names in `source_map.ts` are React's own word and may stay.

## How the work was checked (for whoever continues)

- Unit: `npm test`. Browser: `npm run test:e2e` (builds first, real Chromium, no retries). Guard: `node scripts/guard.ts`. Type check: `npm run typecheck`.
- Performance: the stress scripts used for the investigation are not in the repo. The numbers worth keeping: on a 20 000-element page with 30 unmatched comments a scroll event should stay under 10 ms and idle CPU under about 100 ms per 10 s (`e2e/tests/large_page.spec.ts` asserts generous limits).
- The project rules the work followed: plain everyday names; the agent never resolves a thread; add only what is really needed (no unneeded guards, options or tests); every change shown failing first, then passing, and checked by a second, independent run.
